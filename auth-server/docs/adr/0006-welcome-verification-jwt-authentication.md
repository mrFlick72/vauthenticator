# Welcome and verification challenge APIs require request JWT authentication

For issue [#370](https://github.com/mrFlick72/vauthenticator/issues/370), the agreed authentication boundary for `PUT /api/sign-up/welcome` and `PUT /api/verify-challenge` is an authenticated JWT whose claims are available to the controller's `PermissionValidator`. A browser session alone is insufficient: these operations must not fall back to looking up the session's client application to authorize the request. This preserves authorization against the presented token rather than the client's registered scopes. The intended cleanup removes the duplicate scope rules from `WebSecurityConfig`, consistent with ADRs 0001–0004.

Authenticate these APIs from the bearer JWT supplied with each request and ignore browser sessions, including admin sessions. A request without a JWT returns `401 Unauthorized`. For anonymous requests this contract covers API clients (no `Accept` header or `Accept: application/json`), which get `401` from the bearer entry point without a login redirect; an anonymous browser-like request (`Accept: text/html`) may still be redirected to `/login` by the shared filter chain's form-login entry point, and #370 does not change that. A session must neither substitute for a missing JWT nor supply permissions for a JWT that lacks them. This is a requirement on the request's authentication, not a restriction to the OAuth2 `client_credentials` grant.

The wider policy permits session-based authorization for signup and browser MFA use cases. Browser MFA is an explicit exception because the existing MFA UI uses the session-aware challenge endpoint. The user also explicitly permits JWT authorization or authorization through the session's client application for `PUT /api/accounts/password`; the current implementation requires a JWT, so supporting the session path there would be a separate behavior change. Password flows must be distinguished: mandatory password change during login (`/change-password`), forgotten-password challenge delivery (`/api/reset-password-challenge`), and ticket-based password recovery (`/api/reset-password/{ticket}`) are distinct operations and must not be treated as one blanket session exception. Other API use cases must use JWT authentication without a session fallback. These exceptions do not extend to the welcome-email or email-verification-challenge APIs simply because they concern account onboarding.

For the dual-mode `PUT /api/accounts/password` endpoint, a supplied bearer token takes precedence: an invalid token returns `401`, and a valid JWT without permission returns `403`, even if the session's client application has permission. Consider the session authorization path only when no bearer token is supplied. This interview concerns permission handling; account selection and password-change business logic are outside its scope.

The existing authorization alternatives remain unchanged: the JWT must grant the endpoint's required scope (`Scope.WELCOME` or `Scope.MAIL_VERIFY`), grant `admin:full-access`, or carry the admin role as a granted authority. The admin exceptions are deliberate and do not remove the requirement for JWT authentication.

The `/api/**` `.authenticated()` rule alone does not distinguish JWT authentication from session authentication, so after the two scope rules are removed the JWT requirement must be enforced by the controllers themselves (see *Enforcement decision* below).

#370 verifies this contract with the existing standalone controller test pattern (`standaloneSetup`, a real `PermissionValidator`, `ExceptionAdviceController`, and principals from `SecurityFixture` supplied via `.principal(...)`), not with filter-chain tests. Because the credential-type check lives in `PermissionValidator`, each endpoint's test covers: no principal → `401`; a session-style `UsernamePasswordAuthenticationToken`, including one with the admin role → `401`; a JWT without the endpoint scope → `403`; and a JWT with the endpoint scope, `admin:full-access`, or the admin role → success. Rejected and forbidden cases also assert that the use case is never invoked. What this does not prove is the generic filter-chain behaviour: that anonymous requests are stopped by `/api/**` `.authenticated()` with a bearer `401`, and that a session principal reaches the controller as described. That coverage was deferred to [#386](https://github.com/mrFlick72/vauthenticator/issues/386), which in the end chose not to add filter-chain tests either (ADR 0007). This supersedes the issue's original restriction against adding tests.

## Enforcement decision

The JWT requirement was not enforced as agreed. Both controllers bind a non-null `JwtAuthenticationToken`, so the session fallback in `PermissionValidator` is already unreachable. But a session-only request (form-login `UsernamePasswordAuthenticationToken`, no bearer token) passes `/api/**` `.authenticated()`, and Spring MVC then fails to bind the principal with `IllegalStateException`, which surfaces as `500`, not `401` (reproduced at the MVC level while implementing #370: `Current user principal is not of type [JwtAuthenticationToken]`). Today the `hasAnyAuthority` rules mask this for non-admin sessions (`403`); once they are removed every session-only request reaches the controller. Making the parameter nullable does not help, because the resolver throws whenever a principal of the wrong type is present.

The `401` contract is firm. It is enforced in the controller layer, not in the filter chain:

- Both controllers take `Authentication?` instead of `JwtAuthenticationToken`.
- `PermissionValidator`'s existing JWT-only `validate` is widened to `validate(Authentication?, Scopes)`; it throws `JwtAuthenticationRequiredException` when the authentication is not a `JwtAuthenticationToken`, and otherwise applies the existing JWT scope validation.
- `ExceptionAdviceController` maps `JwtAuthenticationRequiredException` to `401` with `WWW-Authenticate: Bearer`, alongside the existing `InsufficientClientApplicationScopeException` → `403` mapping.
- `EMailVerificationEndPoint` stops passing `HttpSession` to `PermissionValidator`, so the client-app session fallback is no longer reachable from it.

**Considered options:**
- A dedicated stateless `SecurityFilterChain` for these paths (resource server only, no session-backed security context, no form login), which would yield `401` from the bearer entry point — rejected for #370 in favour of keeping authorization, including the credential-type check, in the controller and `PermissionValidator`, consistent with ADRs 0001–0004.
- A rule in the existing filter chain that only accepts `JwtAuthenticationToken` — rejected: denying an already authenticated session goes through the access-denied handler and yields `403`, not `401`.
- An inline `is JwtAuthenticationToken` check returning `401` in each controller — rejected: it duplicates the check per endpoint, which is the drift #370 exists to remove.

**Scope:** the same session-only → `500` behaviour affects every handler that binds `JwtAuthenticationToken` (about 30 handlers). #370 fixes only its two endpoints. The systemic gap, and whether to solve it per controller or with a dedicated filter chain at that scale, is tracked in [#386](https://github.com/mrFlick72/vauthenticator/issues/386). ADR 0007 records the outcome: the per-controller approach was extended to all JWT-only handlers.
