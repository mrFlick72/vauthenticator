# JWT-only APIs enforce the bearer-JWT requirement per controller, not with a dedicated filter chain

For issue [#386](https://github.com/mrFlick72/vauthenticator/issues/386), every `/api/**` handler that bound a `JwtAuthenticationToken` parameter failed with `IllegalStateException` (`500`) when called with a browser session and no bearer token, because `/api/**` `.authenticated()` accepts a form-login session. ADR 0006 fixed this for the welcome and verify-challenge endpoints in the controller layer and left the choice of mechanism for the remaining handlers open. We extended the same per-controller approach to all of them.

- JWT-only handlers bind `Authentication?` and call `PermissionValidator.validate(Authentication?, Scopes)`, which returns the validated `JwtAuthenticationToken` for handlers that need it afterwards (MFA enrolment uses its name and client app id).
- Handlers without a scope check (`PUT /api/accounts`, `PUT /api/accounts/password`) call `PermissionValidator.jwtAuthenticationOf(Authentication?)`, which only requires a bearer JWT. An empty scope set is not used for this, because it would pass by accident and read as a permission check.
- A non-JWT caller gets `JwtAuthenticationRequiredException` → `401` with `WWW-Authenticate: Bearer` (ADR 0006).
- The session-aware endpoints the policy allows, `POST /api/accounts` (signup) and `PUT /api/reset-password-challenge`, bind `Authentication?` and call `PermissionValidator.validate(Authentication?, HttpSession, Scopes)`. A JWT takes precedence; any other authentication, including an already logged-in session user, is treated as "no bearer token" and authorized through the session's client application, the same as an anonymous browser caller.

**Considered options:**
- A dedicated stateless `SecurityFilterChain` for `/api/**` minus the browser session paths (`PUT /api/mfa/challenge`, `GET /api/mfa/enrollment`, `PUT /api/reset-password-challenge`, `PUT /api/reset-password/{ticket}`, `POST /api/accounts`), using only the resource server, so sessions are ignored and a missing JWT yields `401` from the bearer entry point. It would have made JWT-only the default for new endpoints and needed no controller changes. Rejected to keep one enforcement mechanism: the credential-type check stays next to the scope check in `PermissionValidator`, as in ADRs 0001–0004 and 0006, and is covered by the existing standalone controller tests. It would also have made the exclusion list a security-relevant contract, where a forgotten browser path breaks that page.
- Rejecting a logged-in session on signup and the forgotten-password challenge — rejected: being logged in is not a reason to refuse these use cases, and the browser page sends the same session either way.

**Consequences:**
- Every new JWT-only handler must bind `Authentication?` and go through `PermissionValidator`. Binding `JwtAuthenticationToken` directly brings back the `500` for session callers, not an authorization bypass.
- Verification uses the existing standalone controller test pattern only: each JWT-only handler has a "session user, even an admin → `401`" test; the null-authentication case is covered once in `PermissionValidatorTest`. The generic filter-chain behaviour (anonymous requests stopped by `/api/**` `.authenticated()`, a session principal reaching the controller) is deliberately not covered by tests.
- `PUT /api/accounts/password` keeps its `WebSecurityConfig` scope rule, so a non-admin session user is still stopped by the filter chain with `403` before the controller; its migration, and the dual-mode question in ADR 0006, belong to the password migration.
