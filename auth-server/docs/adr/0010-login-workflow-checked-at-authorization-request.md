# The Login Workflow is checked at every authorization request, and the session remembers each Passed Step

For issue [#287](https://github.com/mrFlick72/vauthenticator/issues/287) the Login Workflow (the MFA challenge, then the mandatory password change) stops being a chain of redirects started by the form login `successHandler`. The chain only ran once, right after `POST /login`, and treated a step as done once the browser had been sent to it. A session that left the workflow early, or that was later used for a client app with stricter requirements, was still a fully authenticated Spring session, and `/oauth2/authorize` issued codes for it.

- **The workflow is checked on every `/oauth2/authorize`**, before Spring Authorization Server handles the request. That is the only door where a session becomes a login into a client app. The pages the MFA step needs (`GET /api/mfa/enrollment`, `PUT /api/mfa/challenge`) stay reachable by a session that is not Login-Complete; every MFA write is JWT only (ADR 0007).
- **Each step decides on its own whether it is required** (for this account and this client app) **and whether it is passed.** The check runs the steps in a fixed order, MFA before password change, so a password alone cannot be used to change the password, and redirects to the first step that is required and not passed. Nothing remembers a position in the workflow.
- **The session remembers each Passed Step, not "the workflow passed".** A passed step is skipped on later authorization requests in the same session, for every client app. A step that was skipped because it was not required is not passed and is evaluated again next time. MFA passed in a session is not asked again; logging into an app without `mfa:always` never counts as MFA for an app with it. Account-held steps still read the account (password change reads the mandatory action), so a reset an admin forces mid-session applies at the next authorization unless the account holder already passed that step in this session.
- **A passed step lasts until the session ends**, by logout or expiry. Revoking an MFA Device does not clear it.
- **Every successful password login clears all Passed Steps.** Spring's session fixation protection copies session attributes to the new session id, so without this a second user signing in on the same browser would inherit the first user's passed MFA.
- **After a step is passed, the account holder goes back to the original authorization request**, which runs the check again. Steps never hand off to each other.
- **A login with no client app asking** (no saved authorization request) runs the steps that do not depend on an app, such as password change, straight away. Steps that depend on the app, such as MFA, wait for the first authorization request.
- **Sessions created before this change have no Passed Steps** and are treated like any other session: an `mfa:always` app challenges once. They are not grandfathered.

**Considered options:**
- Keep the redirect chain and fix its cursor (`CompositeLoginWorkflowEngine_index`): rejected. A cursor assumes a step is done once shown, and runs only after `POST /login`, so it cannot catch a session reused for another app or a requirement that appears mid-session.
- Spring Security 7 multi-factor authorization (`FactorGrantedAuthority`, `AllRequiredFactorsAuthorizationManager`): rejected as the model. It describes authentication factors only, and the workflow must hold steps that are not factors (password change today, others later); its missing-factor redirect is also per URL, not per client app. The step model stays in the domain, and Spring is only the adapter that runs the check.
- Keep the user unauthenticated until the workflow finishes (a placeholder `Authentication` promoted at the end): rejected. It does not cover an already authenticated session asking for a stricter app, so the authorization check would be needed anyway.
- Remember "the workflow passed" for the session: rejected. The first app's requirements would count for every later app.

**Consequences:**
- `LoginWorkflowFilter` runs the check in the authorization server filter chain. A step is a `LoginWorkflowHandler` (`id`, page, `isRequiredFor(userName, clientAppId?)`); `CompositeLoginWorkflowEngine` keeps the ordered steps, finds the pending one, and is still the form login success handler. Passed steps are a set of step ids in a session attribute.
- `MfaController` and `ChangePasswordController` hand off to a `LoginWorkflowStepPassedHandler` for their step, which records it as passed and resumes the saved authorization request. The `/login-workflow` page, its session counter and `nextHopeLoginWorkflowSuccessHandler` are gone.
- The MFA step no longer reads `clientId` from the session with an unchecked cast; it takes the client app from the authorization request, and is never required when no app is asking.
- Every active user is asked for MFA once after the deploy when they next open an `mfa:always` app.
- Requiring a step to be passed recently (for example MFA within the last hour) needs the time a step was passed; it is not part of this decision.
